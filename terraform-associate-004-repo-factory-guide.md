# Repo Factory — a zero-cost Terraform project for Associate 004

A complete, self-contained learning project. No Docker. No cloud account. No credit card.
Everything below runs with the Terraform CLI, a free GitHub account, and a free HCP Terraform account.

> **The code in `repo-factory.zip` is canonical.** The snippets in this guide are the teaching
> narrative; the zip contains the finished, fully-commented, parse-checked version. Two differences
> you will notice:
>
> 1. **Naming.** Every managed repository is created as `repo-factory-<key>`, driven by a
>    `name_prefix` variable defaulting to `"repo-factory-"`. The convention is enforced in three
>    places on purpose — inside the module (so no caller can forget it), by a root `check` block
>    (so drift is reported), and by an OPA policy (so it cannot be bypassed even by editing the
>    module). Note the map key stays *unprefixed*: it is the logical name and the Terraform resource
>    address, while the prefixed form is the physical GitHub name. Keeping those separate is what
>    makes the import exercise in M5 instructive.
> 2. **Comments.** Every block in the zip is annotated with what it does in Terraform terms —
>    meta-argument vs argument vs block, why `for_each` over `count`, what `sensitive` does and does
>    not do. Read those as revision material, not decoration.

## Part 1 — Understanding the ask

### The premise

You are pretending to be a platform engineer at a company where developers keep creating GitHub
repositories by hand. Every repo ends up different: some have no README, some have no branch
protection, labels are inconsistent, nobody knows which repos exist.

Your job is to replace that chaos with a **self-service repository factory**: a single Terraform
configuration where adding a repo means adding six lines to a map, opening a pull request, and
letting an automated run apply it — with policy checks that reject non-compliant configurations.

This is a real pattern. Platform teams genuinely build this. It is also, conveniently, an almost
perfect vehicle for the exam objectives.

### Why this project instead of "spin up an EC2 instance"

| What the exam tests | What you need to see it happen |
|---|---|
| Providers, plugins, lock file | Any provider |
| HCL, variables, functions, meta-arguments | Any provider |
| Modules and versioning | Any provider |
| State, drift, import, refresh | **A real remote API you can change outside Terraform** |
| HCP Terraform, VCS runs, policy | HCP Terraform |

The only thing a cloud account buys you is a slightly more familiar resource name in the `plan`
output. GitHub gives you the one genuinely irreplaceable ingredient — a real remote system with a
real API that other people (and you, via a web UI) can change behind Terraform's back. That is
where drift, import, and reconciliation stop being abstract.

### Completion goal (your definition of done)

You are finished when **all** of these are true:

1. A public GitHub repo named `repo-factory` contains your configuration.
2. It provisions **at least 3 repositories** driven by a single `map(object(...))` variable — adding a
   repo requires editing only that map, nothing else.
3. Each managed repo gets: a README rendered from a template, a consistent label set, branch
   protection, a deploy key generated by Terraform, and topics.
4. The repo logic lives in a **local module** that is also consumed from a **Git source with a version
   tag**, using a version constraint.
5. State lives in **HCP Terraform**, and runs are **VCS-driven** — you push, HCP Terraform plans.
6. **One OPA policy set** blocks at least one class of non-compliant config, and you have a screenshot
   or log of it failing a run.
7. At least one repo was **created by hand and imported** into state.
8. Your README documents *why* you made each structural choice, not just what the code does.
9. You can run these twelve commands from memory and explain what each does:
   `init`, `validate`, `plan`, `apply`, `destroy`, `fmt`, `state list`, `state show`, `state mv`,
   `state rm`, `import`, `output`.

If you hit 1–9, you have covered every 004 objective with hands-on evidence. That is the bar.

### Stretch goals (only after completion)

- **S1 — Terraform manages Terraform.** Use the `tfe` provider to create your own HCP Terraform
  workspaces, variable sets, and projects as code.
- **S2 — Run triggers.** Split into two workspaces (`platform` and `repos`) where the first's output
  triggers the second.
- **S3 — Native tests.** Write `.tftest.hcl` files and run `terraform test` against your module.
- **S4 — Terraform 1.12 features.** Use `ephemeral` resources and write-only arguments for the deploy
  key so the private key never lands in state. This is the most exam-current thing on the list.
- **S5 — Private module registry.** Publish your module to HCP Terraform's private registry and
  consume it by registry address.

### Milestones and what each one teaches

| # | Milestone | 004 objective | The thing you actually learn |
|---|---|---|---|
| M0 | Setup and first apply | 1, 2, 3 | The core workflow is a loop, not a ceremony |
| M1 | Configuration language | 4 | Variable precedence, types, validation, functions |
| M2 | Extract a module | 5 | Inputs/outputs are an API contract |
| M3 | Point it at GitHub | 2, 3 | Real providers fail in real ways |
| M4 | State surgery | 6 | State is a file you own, not magic |
| M5 | Drift and import | 6, 7 | Terraform reconciles, it does not remember |
| M6 | HCP Terraform | 8 | Remote execution changes where variables live |
| M7 | Policy and CI | 8 | Governance is a gate, not a suggestion |

Roughly one milestone per two days at an hour a day. M4 and M5 deserve double time — they are the
densest part of the exam and the part people fail on.

## Part 2 — Setup

### Prerequisites

```bash
terraform version   # need 1.12.x to match the exam
git --version
```

If Terraform is not installed, download the binary from `developer.hashicorp.com/terraform/install`
and put it on your `PATH`. A single static binary — no admin rights needed if you place it in your
home directory.

### GitHub token

1. Create a free personal GitHub account (or use yours).
2. Settings → Developer settings → Personal access tokens → **Fine-grained tokens** → Generate.
3. Scope it to **all repositories you own**, with these permissions:
   - Administration: Read and write
   - Contents: Read and write
   - Issues: Read and write
   - Metadata: Read
   - Secrets: Read and write
4. Export it. **Never put it in a `.tf` file.**

```bash
export GITHUB_TOKEN="github_pat_..."
export GITHUB_OWNER="your-github-username"
```

> **Company laptop note:** check your IT policy before putting a personal PAT on a work machine. If
> that is a problem, every milestone except M3 and M5 works with local providers alone — substitute
> `local_file` resources for `github_repository` and you still cover 7 of 8 objectives.

### HCP Terraform account

Sign up at `app.terraform.io`. Create an organisation. The Free plan is permanent, needs no card, and
covers 500 managed resources — you will use about thirty.

## Part 3 — Milestone by milestone

### M0 — First apply, no GitHub yet

The point of M0 is to burn the core workflow into your fingers before any real API is involved.

**`versions.tf`**

```hcl
terraform {
  required_version = "~> 1.12"

  required_providers {
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}
```

**`main.tf`**

```hcl
resource "random_pet" "name" {
  length    = 2
  separator = "-"
}

resource "local_file" "manifest" {
  filename        = "${path.module}/out/manifest.txt"
  content         = "repo: ${random_pet.name.id}\n"
  file_permission = "0644"
}
```

Now run the loop, slowly, reading every line of output:

```bash
terraform init
terraform fmt -check       # fails; then run `terraform fmt` and see the diff
terraform validate
terraform plan
terraform apply
terraform show
terraform destroy
```

**Things to actually do, not just read:**

- `cat terraform.tfstate` and find `random_pet.name`. Notice `"mode": "managed"` and the `serial`
  counter. Apply again and watch `serial` increment.
- `cat .terraform.lock.hcl`. Note the recorded version and hashes. Change `~> 3.6` to `~> 3.5`, run
  `terraform init` — it fails. Run `terraform init -upgrade` — it succeeds and rewrites the lock file.
- Delete `out/manifest.txt` by hand, then `terraform plan`. Terraform wants to recreate it. That is
  drift, in miniature.
- Run `terraform apply -auto-approve` and notice no prompt appeared.

**Self-check:** what is the difference between `terraform validate` and `terraform plan`, and which
one needs `init` to have run? (Both need init; `validate` checks syntax and internal consistency
without contacting providers' APIs, `plan` contacts them and refreshes state.)

### M1 — Configuration language

Now make everything configurable. This milestone is pure objective 4, which is heavily weighted.

**`variables.tf`**

```hcl
variable "org_name" {
  description = "Logical name of the platform team owning these repos."
  type        = string
  default     = "platform"

  validation {
    condition     = can(regex("^[a-z][a-z0-9-]{2,20}$", var.org_name))
    error_message = "org_name must be lowercase alphanumeric with hyphens, 3-21 chars."
  }
}

variable "default_labels" {
  description = "Labels applied to every managed repository."
  type = map(object({
    color       = string
    description = string
  }))

  default = {
    bug           = { color = "d73a4a", description = "Something is broken" }
    enhancement   = { color = "a2eeef", description = "New feature or request" }
    "tech-debt"   = { color = "fbca04", description = "Cleanup work" }
    "needs-triage" = { color = "ededed", description = "Not yet assessed" }
  }

  validation {
    condition = alltrue([
      for name, l in var.default_labels : can(regex("^[0-9a-fA-F]{6}$", l.color))
    ])
    error_message = "Every label colour must be a 6-digit hex code without a leading #."
  }
}

variable "repositories" {
  description = "The repositories this factory manages. Key is the repo name."
  type = map(object({
    description        = string
    topics             = optional(list(string), [])
    visibility         = optional(string, "public")
    required_reviewers = optional(number, 0)
    extra_labels = optional(map(object({
      color       = string
      description = string
    })), {})
  }))
  default = {}

  validation {
    condition = alltrue([
      for name, r in var.repositories : can(regex("^[a-z0-9][a-z0-9._-]{0,99}$", name))
    ])
    error_message = "Repository names must be lowercase and URL-safe."
  }

  validation {
    condition = alltrue([
      for name, r in var.repositories : contains(["public", "private"], r.visibility)
    ])
    error_message = "visibility must be either 'public' or 'private'."
  }
}

variable "github_owner" {
  description = "GitHub user or org that owns the repositories."
  type        = string
}
```

Note the two separate `validation` blocks on one variable — allowed since 1.9, and it gives you
better error messages than one compound condition.

**Now the variable precedence experiment.** This is worth twenty minutes on its own because it is
almost guaranteed to appear on the exam.

Create four things setting the same variable:

```bash
# 1. terraform.tfvars
echo 'org_name = "from-tfvars"' > terraform.tfvars

# 2. an auto-loaded file
echo 'org_name = "from-auto"' > zz.auto.tfvars

# 3. an environment variable
export TF_VAR_org_name="from-env"

# 4. the command line
terraform plan -var 'org_name=from-cli'
```

Run `terraform console` and type `var.org_name` after each combination. Work out the order
empirically, then confirm it against the docs. (Lowest to highest: environment variable →
`terraform.tfvars` → `*.auto.tfvars` in lexical order → `-var-file` → `-var`.)

**Add locals, functions, and a data source.** In `main.tf`:

```hcl
locals {
  managed_by = "terraform"
  timestamp  = formatdate("YYYY-MM-DD", timestamp())

  # Merge default labels with per-repo extras
  repo_labels = {
    for name, cfg in var.repositories :
    name => merge(var.default_labels, cfg.extra_labels)
  }

  # Flatten to a set of composite keys for a future for_each
  label_pairs = merge([
    for repo, labels in local.repo_labels : {
      for label, cfg in labels : "${repo}:${label}" => {
        repo  = repo
        label = label
        color = cfg.color
      }
    }
  ]...)
}

data "http" "gitignore_template" {
  url = "https://raw.githubusercontent.com/github/gitignore/main/Terraform.gitignore"

  request_headers = {
    Accept = "text/plain"
  }

  retry {
    attempts = 2
  }
}

check "gitignore_fetch_succeeded" {
  assert {
    condition     = data.http.gitignore_template.status_code == 200
    error_message = "Could not fetch the upstream .gitignore template."
  }
}
```

The `merge([...]...)` spread trick for flattening nested maps is worth understanding — it is the
idiomatic answer to "I have a map of maps and I need a flat `for_each`".

**Exercises:**

- Open `terraform console` and evaluate `local.label_pairs`, `keys(var.default_labels)`,
  `lookup(var.default_labels, "bug", null)`, `try(var.repositories["nope"].description, "missing")`.
- Add an output marked `sensitive = true` and observe how `terraform output` behaves versus
  `terraform output -json`.
- Deliberately break a validation rule and read the error.

**Self-check:** what is the difference between a `check` block and a variable `validation` block, and
when does each run? (Validation runs at plan time and blocks; a `check` block runs after apply as a
non-blocking assertion that produces a warning.)

### M2 — Extract the module

**`modules/repo/versions.tf`**

```hcl
terraform {
  required_version = "~> 1.12"

  required_providers {
    github = {
      source  = "integrations/github"
      version = "~> 6.0"
    }
    tls = {
      source  = "hashicorp/tls"
      version = "~> 4.0"
    }
  }
}
```

A module declares `required_providers` but **never** a `provider` block. Providers are configured in
the root and inherited. That distinction is exam material.

**`modules/repo/variables.tf`**

```hcl
variable "name" {
  description = "Repository name."
  type        = string
}

variable "description" {
  description = "Repository description."
  type        = string
}

variable "visibility" {
  description = "public or private."
  type        = string
  default     = "public"
}

variable "topics" {
  description = "Repository topics."
  type        = list(string)
  default     = []
}

variable "labels" {
  description = "Issue labels to create."
  type = map(object({
    color       = string
    description = string
  }))
  default = {}
}

variable "protect_default_branch" {
  description = "Apply branch protection to the default branch."
  type        = bool
  default     = true
}

variable "required_reviewers" {
  description = "Approving reviews required before merge."
  type        = number
  default     = 0

  validation {
    condition     = var.required_reviewers >= 0 && var.required_reviewers <= 6
    error_message = "GitHub allows between 0 and 6 required reviewers."
  }
}

variable "gitignore_content" {
  description = "Contents of the .gitignore file to commit."
  type        = string
  default     = ""
}

variable "managed_by" {
  description = "Free-text marker written into the generated README."
  type        = string
  default     = "terraform"
}
```

**`modules/repo/main.tf`**

```hcl
resource "github_repository" "this" {
  name        = var.name
  description = var.description
  visibility  = var.visibility

  auto_init              = true
  has_issues             = true
  has_wiki               = false
  has_projects           = false
  vulnerability_alerts   = true
  delete_branch_on_merge = true
  topics                 = var.topics

  lifecycle {
    # Branch protection on private repos needs a paid GitHub plan.
    precondition {
      condition     = !(var.protect_default_branch && var.visibility == "private")
      error_message = "Branch protection on a private repo requires GitHub Pro or Team. Set visibility = \"public\" or protect_default_branch = false."
    }
  }
}

resource "github_branch_protection" "this" {
  count = var.protect_default_branch ? 1 : 0

  repository_id = github_repository.this.node_id
  pattern       = github_repository.this.default_branch

  enforce_admins          = false
  allows_force_pushes     = false
  allows_deletions        = false
  required_linear_history = true

  required_pull_request_reviews {
    required_approving_review_count = var.required_reviewers
    dismiss_stale_reviews           = true
  }
}

resource "github_issue_label" "this" {
  for_each = var.labels

  repository  = github_repository.this.name
  name        = each.key
  color       = each.value.color
  description = each.value.description
}

resource "tls_private_key" "deploy" {
  algorithm = "ED25519"
}

resource "github_repository_deploy_key" "this" {
  title      = "terraform-managed-readonly"
  repository = github_repository.this.name
  key        = tls_private_key.deploy.public_key_openssh
  read_only  = true
}

resource "github_repository_file" "readme" {
  repository = github_repository.this.name
  branch     = github_repository.this.default_branch
  file       = "README.md"

  content = templatefile("${path.module}/templates/README.md.tftpl", {
    name        = var.name
    description = var.description
    topics      = var.topics
    labels      = keys(var.labels)
    managed_by  = var.managed_by
  })

  commit_message      = "chore(terraform): sync README"
  overwrite_on_create = true
}

resource "github_repository_file" "gitignore" {
  count = var.gitignore_content == "" ? 0 : 1

  repository          = github_repository.this.name
  branch              = github_repository.this.default_branch
  file                = ".gitignore"
  content             = var.gitignore_content
  commit_message      = "chore(terraform): sync .gitignore"
  overwrite_on_create = true
}
```

**`modules/repo/templates/README.md.tftpl`**

```
# ${name}

${description}

> Managed by ${managed_by}. Do not edit this file directly — change the Terraform configuration.

## Topics
%{ for t in topics ~}
- ${t}
%{ endfor ~}

## Issue labels
%{ for l in labels ~}
- `${l}`
%{ endfor ~}
```

**`modules/repo/outputs.tf`**

```hcl
output "full_name" {
  description = "owner/repo identifier."
  value       = github_repository.this.full_name
}

output "node_id" {
  description = "GraphQL node ID, needed for branch protection references."
  value       = github_repository.this.node_id
}

output "clone_url" {
  description = "HTTPS clone URL."
  value       = github_repository.this.http_clone_url
}

output "deploy_private_key" {
  description = "Private half of the generated deploy key."
  value       = tls_private_key.deploy.private_key_openssh
  sensitive   = true
}
```

**Self-check:** `deploy_private_key` is marked sensitive — is it therefore encrypted in state? (No.
State stores it in plaintext. `sensitive` only suppresses CLI output. This is why state files must be
treated as secrets, and why stretch goal S4 — write-only arguments — matters.)

### M3 — Wire it up

**`providers.tf`**

```hcl
provider "github" {
  owner = var.github_owner
  # Token comes from the GITHUB_TOKEN environment variable.
}

provider "tls" {}
```

**`main.tf` (root, replacing M0's contents)**

```hcl
module "repo" {
  source   = "./modules/repo"
  for_each = var.repositories

  name                   = each.key
  description            = each.value.description
  visibility             = each.value.visibility
  topics                 = each.value.topics
  labels                 = local.repo_labels[each.key]
  required_reviewers     = each.value.required_reviewers
  protect_default_branch = each.value.visibility == "public"
  gitignore_content      = data.http.gitignore_template.response_body
  managed_by             = "${var.org_name} platform team"
}
```

**`terraform.tfvars`**

```hcl
github_owner = "your-github-username"
org_name     = "platform"

repositories = {
  "svc-billing" = {
    description        = "Billing service"
    topics             = ["service", "go"]
    required_reviewers = 0
    extra_labels = {
      "area/payments" = { color = "5319e7", description = "Payments subsystem" }
    }
  }

  "svc-notifications" = {
    description = "Notification fan-out service"
    topics      = ["service", "python"]
  }

  "lib-common" = {
    description = "Shared internal library"
    topics      = ["library"]
    extra_labels = {
      "breaking-change" = { color = "b60205", description = "Requires a major version bump" }
    }
  }
}
```

**`outputs.tf`**

```hcl
output "managed_repositories" {
  description = "All repositories under management."
  value       = { for k, m in module.repo : k => m.full_name }
}

output "clone_urls" {
  description = "Clone URLs keyed by repo name."
  value       = { for k, m in module.repo : k => m.clone_url }
}

output "repository_count" {
  description = "How many repos this factory manages."
  value       = length(module.repo)
}
```

Then:

```bash
terraform init
terraform plan
terraform apply
```

**Things that will go wrong, and that is the point:**

- **403 on branch protection.** Your token is missing the Administration permission. Fix the token,
  re-run. Notice Terraform did *not* roll back the repos it already created — partial apply is real.
- **Repo name already exists.** GitHub returns 422. Terraform reports it against one `for_each` key
  and continues with the others.
- **Eventual consistency.** Occasionally `github_repository_file` fails because the repo's default
  branch is not ready. Re-run `apply`. This is exactly why Terraform is idempotent and why re-running
  is a legitimate strategy.

**Exercises:**

- Change `required_reviewers` from 0 to 1 on one repo. Run `plan`. Note it is an **update in place**,
  not a replace.
- Change a repo's `name` in the map key. Run `plan`. Note it is a **destroy and create** — and that
  the resource address changed too. Do not apply this yet; you will fix it properly with `moved` in M4.
- Add `-out=tfplan` to your plan and then `terraform apply tfplan`. Note that the saved plan does not
  re-prompt and does not re-refresh.
- Run `terraform plan -target=module.repo[\"lib-common\"]` and read the warning Terraform prints
  about targeting being for exceptional circumstances.

### M4 — State surgery

**Do not skip this. It is the densest exam material and it is entirely hands-on.**

Work through every command below. After each destructive one, verify with `terraform plan` that the
world still matches your intent.

```bash
# Inventory
terraform state list
terraform state list 'module.repo["svc-billing"]'
terraform state show 'module.repo["svc-billing"].github_repository.this'

# Back it up before you break anything
terraform state pull > backup.tfstate

# Rename without destroying: first try the wrong way
# (edit the map key svc-billing -> service-billing, run plan, see destroy/create, DON'T apply)

# Now the right way — add a moved block to main.tf:
```

```hcl
moved {
  from = module.repo["svc-billing"]
  to   = module.repo["service-billing"]
}
```

```bash
terraform plan   # now shows a move, not a destroy
terraform apply
# then delete the moved block once applied — it has done its job
```

Then the manual equivalent, so you understand what `moved` automates:

```bash
terraform state mv 'module.repo["lib-common"]' 'module.repo["library-common"]'
terraform state list   # confirm the address changed
# revert it
terraform state mv 'module.repo["library-common"]' 'module.repo["lib-common"]'
```

**Detach and reattach** — the classic import drill:

```bash
terraform state rm 'module.repo["lib-common"].github_repository.this'
terraform plan
# Terraform now wants to CREATE a repo that already exists. It will fail on apply (422).
# State is Terraform's only memory. Removing from state does not delete anything real.

terraform import 'module.repo["lib-common"].github_repository.this' lib-common
terraform plan   # back to no changes
```

**Other commands to run and understand:**

```bash
terraform state show -json 'module.repo["svc-notifications"].github_issue_label.this["bug"]'
terraform refresh                 # deprecated alias
terraform apply -refresh-only     # the modern form — updates state, changes nothing real
terraform plan -refresh=false     # skips refresh entirely
terraform providers
terraform providers lock -platform=linux_amd64 -platform=darwin_arm64
terraform graph | head -40
terraform force-unlock <LOCK_ID>  # read the docs; you will need this after an interrupted apply
```

To actually experience a lock, start an apply and kill it with Ctrl+C twice mid-run, then try another
apply. You will get a lock error with an ID. That is when `force-unlock` earns its place.

`terraform state replace-provider` is the one command you cannot easily demo here — it swaps the
provider source address for every matching resource in state, used when a provider is renamed or when
migrating between registries. Read the doc page and know what it is for.

**Self-check:** you run `terraform state rm` on a resource and then `terraform destroy`. What happens
to that real-world object? (Nothing — it is orphaned. Terraform no longer knows about it.)

### M5 — Drift and import

**Cause drift deliberately.**

1. In the GitHub web UI, open one of your repos → Issues → Labels → delete the `tech-debt` label.
2. Change another repo's description in the UI.
3. Add a topic in the UI that is not in your config.

Then:

```bash
terraform plan
```

Read the output carefully. Terraform reports what it found during refresh separately from what it
intends to change. Note that Terraform will *revert* your UI changes — the configuration is the source
of truth. This is the whole argument for IaC in one screen of output.

```bash
terraform apply -refresh-only   # accept reality into state WITHOUT reverting
terraform plan                  # now shows the config drift as pending changes
terraform apply                 # reconcile back to config
```

**Import a hand-made repo.** In the GitHub UI, create a repo called `legacy-service` manually. Then:

```hcl
# import.tf — a temporary file
import {
  to = github_repository.legacy
  id = "legacy-service"
}
```

```bash
terraform plan -generate-config-out=generated.tf
```

Open `generated.tf`. Terraform has written a resource block matching reality. Move the useful parts
into your module map, delete the scaffolding, and re-import to the module address:

```hcl
import {
  to = module.repo["legacy-service"].github_repository.this
  id = "legacy-service"
}
```

```bash
terraform plan    # should show the repo being adopted, plus the labels/README being added
terraform apply
# delete import.tf once complete
```

**Self-check:** what is the difference between the `import` block and the `terraform import` command?
(The block is declarative, plannable, reviewable in a PR, and can generate configuration. The command
is imperative and mutates state immediately with no plan step. The block is the modern default.)

### M6 — HCP Terraform

This is objective 8 — a full eighth of the exam and the part 003-era material does not cover.

**Migrate the backend.** Add to `versions.tf`:

```hcl
terraform {
  required_version = "~> 1.12"

  cloud {
    organization = "your-org-name"

    workspaces {
      name = "repo-factory-sandbox"
    }
  }

  required_providers { /* ... unchanged ... */ }
}
```

```bash
terraform login          # opens a browser, stores a token in ~/.terraform.d/
terraform init           # prompts to migrate existing state — say yes
terraform state list     # same resources, now stored remotely
```

Open the workspace in the HCP Terraform UI and look at the **States** tab. Every apply is versioned
and diffable. That alone is worth the migration.

**Set variables in the workspace.** Because execution is now remote, your local `GITHUB_TOKEN` is not
available to runs. In the workspace, add:

- Environment variable `GITHUB_TOKEN`, marked **sensitive**.
- Terraform variable `github_owner`.

Run `terraform plan` locally and watch it stream from a remote runner. Note that the plan is executing
on HashiCorp's infrastructure, not your laptop.

**Connect VCS.** Push your `repo-factory` directory to a public GitHub repo, then in the workspace:
Settings → Version Control → connect to that repo. From now on, pushing to a branch triggers a
speculative plan and opening a PR shows the plan inline. Merging to `main` queues an apply.

Test it: change a label colour, open a PR, and read the plan comment.

**Variable sets.** Create a variable set at the organisation level containing `GITHUB_TOKEN`, and
apply it to all workspaces. Remove the workspace-level copy. This is how you avoid pasting secrets
into ten workspaces.

**Projects.** Create a project called `platform` and move the workspace into it. Projects are the
newer grouping and permission boundary — 004 tests that they exist and what they are for.

**Execution modes.** In workspace settings, switch between Remote and Local execution and observe the
difference in where the plan runs. Understand that Local mode still stores state remotely.

**Self-check:** name three things a CLI workspace (`terraform workspace new`) is *not*. (It is not an
HCP Terraform workspace; it does not isolate configuration, only state; it does not provide separate
variables or credentials. Conflating the two is a classic exam trap.)

### M7 — Policy and CI

**An OPA policy.** Create `policies/repo-standards.rego`:

```rego
package terraform

import rego.v1

# Deny any repository that is not public.
deny contains msg if {
	some rc in input.plan.resource_changes
	rc.type == "github_repository"
	rc.change.after.visibility != "public"
	msg := sprintf("Repository %q must be public on the free plan, got %q", [rc.change.after.name, rc.change.after.visibility])
}

# Deny repositories with no description.
deny contains msg if {
	some rc in input.plan.resource_changes
	rc.type == "github_repository"
	trim_space(object.get(rc.change.after, "description", "")) == ""
	msg := sprintf("Repository %q must have a description", [rc.change.after.name])
}

# Deny repositories with no topics — forces discoverability.
deny contains msg if {
	some rc in input.plan.resource_changes
	rc.type == "github_repository"
	count(object.get(rc.change.after, "topics", [])) == 0
	msg := sprintf("Repository %q must declare at least one topic", [rc.change.after.name])
}
```

Add a `policies/policies.hcl` describing the set:

```hcl
policy "repo-standards-visibility" {
  query          = "data.terraform.deny"
  enforcement_level = "mandatory"
}
```

In HCP Terraform: Settings → Policy Sets → Connect a VCS repo → point at the `policies/` directory,
select OPA, and scope it to your workspace. The free plan allows one policy set with up to five
policies, which is exactly what you need.

**Now prove it works.** Add a repo to your map with `visibility = "private"`, push, and watch the run
fail at the policy check stage with your error message. Screenshot it — that is completion criterion 6.

**CI for the config itself.** `.github/workflows/terraform.yml`:

```yaml
name: terraform

on:
  pull_request:
  push:
    branches: [main]

jobs:
  checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: 1.12.2
          cli_config_credentials_token: ${{ secrets.TF_API_TOKEN }}

      - name: Format check
        run: terraform fmt -check -recursive

      - name: Init
        run: terraform init -backend=false

      - name: Validate
        run: terraform validate
```

GitHub Actions minutes are unlimited on public repositories, so this costs nothing. Note
`-backend=false` — validation does not need remote state, and this avoids needing credentials for the
format and syntax gate.

## Part 5 — Stretch goals, briefly

**S4 is the highest-value one** because it is specific to Terraform 1.12, which is exactly the version
004 tests. Replace the deploy-key handling with ephemeral resources so the private key never touches
state:

```hcl
ephemeral "tls_private_key" "deploy" {
  algorithm = "ED25519"
}
```

Ephemeral values exist only during a single operation. They cannot be referenced from persistent
attributes, only from other ephemeral contexts and write-only arguments. Getting this to compile will
teach you the constraint model faster than any doc page.

**S1** — the `tfe` provider managing your own HCP Terraform workspaces — is the best portfolio piece,
because it demonstrates you understand the control plane and not just the resources.

## Part 6 — Study rhythm

- **Weeks 1–2:** M0 through M5. Code every day, even for twenty minutes.
- **Week 3:** M6 and M7, plus the [official learning path](https://developer.hashicorp.com/terraform/tutorials/certification-004/associate-study-004).
- **Week 4:** The [exam content list](https://developer.hashicorp.com/terraform/tutorials/certification-004/associate-review-004) as a line-by-line checklist, the official sample questions, and a slow read of the CLI reference docs — the exam asks about flags and command behaviour that no tutorial mentions.

Two habits that matter more than the code:

1. **Write down why, not what.** Every structural decision goes in your README. "I used `for_each`
   instead of `count` here because removing a middle element with `count` would recreate everything
   after it." That sentence is worth more than the diff.
2. **Break things deliberately.** Every hour of debugging your own broken state teaches more than
   three hours of watching videos. The exam rewards people who have seen Terraform fail.

Skip exam dumps. They will not prepare you for scenario questions, and you will have built something
real by the end of this instead.
